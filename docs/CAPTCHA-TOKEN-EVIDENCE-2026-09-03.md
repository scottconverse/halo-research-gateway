## Decision and scope

Choices were to keep the token adapter disconnected, add broad scripted forms,
or connect explicit research-gate widgets to the existing crawler. Chose the
third because it directly helps read/cite blocked public sources without adding
account actions. No model-selected scripts, hidden CAPTCHA internals, password
entry, general form API, new dependency or provider enablement was added.

Automatic public crawling only; no managed profile, local target, recognized
sensitive URL or explicit interaction. The existing exact-domain, encrypted
connection, attempt and estimated-spend controls must permit the solver request.
One supported widget, bounded key/callback/field metadata, callable declared
callback, unchanged URL/widget and a printable bounded returned token are required.
The final source must be readable, no longer recognized as a challenge and have
a successful observed HTTP status. An original 403 with only a DOM change remains
an error; a main-frame navigation to a real 200 can succeed. Reflected exact tokens
are redacted from evidence; token-bearing citation/navigation URLs are rejected.

The browser invokes a site's declared callback; site JavaScript remains untrusted
and executes under the existing browser network policy. This is not a universal
proof that arbitrary site scripts are read-only or that every secret is detected.

optional-provider/paid adapters, HTML extraction and neighboring tests; new test
files and token module; affected README/manual/status/changelog/config; gate and
manifest scripts. Existing browser/challenge classification and provider budgets

  corrected. These intermediate full outputs are not in the retained raw stores.

  those were repaired. That first tool output was truncated, not a complete log.
- Native MCP test initially used `isError` instead of the SDK's `is_error`;
  three failures were test-author errors, corrected without changing production.
- A genuine native 403-to-200 navigation failed because Crawl4AI retained the
  original response status. A test-only diagnostic showed original status 403,

  extracts the actual verified browser state and observed final status, without
  flipping Crawl4AI's flag. Diagnostic instrumentation was removed. The focused
  intermediate diagnostic output is not a complete retained raw transcript.
- An unknown configured solver blocked an ordinary non-challenge article. The
  assertion failed, then passed after checking for a challenge before selecting
  the solver. Ordinary articles never invoke it.
- Oversized callbacks/response-field names and a control-character field reached
  the solver. Three assertion failures preceded bounded metadata validation.
- Negative coverage includes missing/ambiguous widgets, unsupported hCaptcha,

## What the native test actually proves

Three retrieval cases use actual Windows Chrome, two independent network MCP
clients, a disposable Gateway/database and an aiohttp loopback fake solver.
The fake vendor validates task/key/URL; browser JavaScript validates the exact
token and response field before exposing source text or navigating to `/source`.
Assertions cover readable final source, final URL/status, provenance, no reflected
token/key in MCP output, one shared vendor attempt and owned-browser cleanup.
All observed fixture browser requests are GETs. This does not constrain all real
site JavaScript to GET or prove production vendor transport compatibility.

The fourth native case cancels the crawler directly while its fake vendor waits.
It verifies no callback application and native child cleanup. Two MCP sessions
exist, but cancellation is **not** triggered through an MCP client disconnect.
That distinction is intentional; no MCP-disconnect solver claim is made.

Existing paid-adapter, budgets and challenge-routing unit checks were widened
together (`69 passed in 4.83s` before three final metadata tests). No real vendor
endpoint was contacted, no paid account connected, and no installed policy changed.
